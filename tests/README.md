# Test Strategy

## Структура

tests/
├── unit/
├── integration/
├── e2e/
├── security/
├── migrations/
└── sync/

## Unit

Проверять доменные правила без сети и UI:

- переходы задач между дорожками;
- системные состояния;
- даты и временные зоны;
- категории;
- Markdown-чек-листы;
- двустороннее обновление чек-листа и задачи;
- правила напоминаний.

## Integration

Проверять:

- репозитории и локальную БД;
- транзакции;
- миграции;
- API;
- загрузку вложений;
- журнал синхронизации.

## Sync

Обязательные сценарии:

- offline → online;
- повтор отправки операции;
- разрыв соединения во время пакета;
- две операции с одним ID;
- параллельное изменение на двух устройствах;
- удаление против редактирования;
- длительное отсутствие устройства;
- восстановление после переустановки клиента;
- сервер недоступен при запуске приложения.

## E2E

Проверять основные пользовательские потоки на каждой платформе:

- создать заметку;
- создать задачу;
- связать задачу с пунктом чек-листа;
- изменить состояние с обеих сторон;
- просмотреть задачу в календаре/Ганте;
- синхронизировать между устройствами;
- разрешить конфликт.

## Security

- аутентификация и авторизация;
- недопустимые ID/поля;
- загрузка файлов;
- секреты и токены;
- prompt injection;
- массовые операции;
- проверка резервных копий и восстановления.

## Правила

- Тест должен проверять поведение, а не внутреннюю реализацию
  без необходимости.
- Не использовать production-данные.
- Тесты должны быть воспроизводимыми.
- Ошибка теста не должна автоматически приводить
  к удалению данных или сбросу среды.
- Тестовые секреты должны быть фиктивными.
