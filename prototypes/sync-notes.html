Шаг 2 · только NOTE · нужно ОК

Первый sync-срез: заметки

Шаг добавляет серверную синхронизацию только для `NOTE`. Клиентский sync engine, задачи, связи и вложения — следующими шагами.

push / pull idempotency cursor tombstone только NOTE без клиента

Входит

change_log, processed_operations, push/pull/state, CREATE/UPDATE/DELETE, конфликты, тесты.

Не входит

клиентский sync, UI, tasks, lanes, links, attachments, rate limiting, VPN.

Результат

Два устройства могут создать и изменить заметку через сервер без дублей и молчаливой потери данных.

POST /api/v1/sync/push

До 100 операций. Каждая операция — отдельная транзакция; частичный успех допустим.

{ "operations": [ { "operationId": "a1...uuid", "deviceId": "5d0f...uuid", "entityType": "NOTE", "entityId": "9c...uuid", "operationType": "UPDATE", "baseRevision": 3, "clientTimestamp": "2026-11-05T20:30:00Z", "payload": { "title": "Заметка", "contentMarkdown": "# Текст", "categoryId": "work" } } ] }

Результат по операции

{ "results": [ { "operationId": "a1...uuid", "status": "APPLIED", "entityId": "9c...uuid", "revision": 4, "changeSeq": 128 }, { "operationId": "b2...uuid", "status": "CONFLICT", "entityId": "7d...uuid", "revision": 9, "serverEntity": { "id": "7d...uuid", "title": "Серверная", "contentMarkdown": "...", "categoryId": "personal", "revision": 9, "updatedAt": "2026-11-05T20:31:00Z", "deletedAt": null } }, { "operationId": "c3...uuid", "status": "REJECTED", "code": "VALIDATION_ERROR", "message": "Заголовок обязателен" } ] }

Порядок обработки

01Проверить operationId
→
02Проверить entityType
→
03Проверить baseRevision
→
04Применить в транзакции
→
05change_log

CREATE

baseRevision = null. Новая заметка получает revision 1. Если entityId уже существует — REJECTED.

UPDATE

baseRevision обязательна. revision увеличивается на 1. Несовпадение — CONFLICT.

DELETE

baseRevision обязательна. Устанавливается deletedAt, revision +1, пишется tombstone.

DUPLICATE

Повтор operationId с тем же телом возвращает прежний результат, не создаёт изменение.

GET /api/v1/sync/pull

Изменения после cursor, по возрастанию seq. Tombstones включены. Cursor двигается только после применения.

GET /api/v1/sync/pull?cursor=127&limit=200 Authorization: Bearer <access> 200 OK { "changes": [ { "seq": 128, "entityType": "NOTE", "entityId": "9c...uuid", "operationId": "a1...uuid", "operationType": "UPDATE", "revision": 4, "originDeviceId": "5d0f...uuid", "changedAt": "2026-11-05T20:30:01Z", "payload": { "id": "9c...uuid", "title": "Заметка", "contentMarkdown": "# Текст", "categoryId": "work", "revision": 4, "updatedAt": "2026-11-05T20:30:01Z", "deletedAt": null } } ], "nextCursor": "128", "hasMore": false }

Cursor

Непрозрачная строка. Начальное значение 0. При ошибке применения не сдвигается.

Пагинация

limit 1..500, по умолчанию 200. hasMore требует повторного запроса.

Собственные изменения

Возвращаются тоже. Повторное применение снимка идемпотентно.

Пустая страница

nextCursor = текущий cursor, hasMore = false.

Конфликт заметки

baseRevision не совпала → сервер не перезаписывает данные и возвращает полный снимок.

01Клиент: baseRevision 3
→
02Сервер: revision 5
→
03CONFLICT + serverEntity
→
04Выбор пользователя
{ "operationId": "b2...uuid", "status": "CONFLICT", "entityId": "7d...uuid", "revision": 5, "serverEntity": { "id": "7d...uuid", "title": "Версия с другого устройства", "contentMarkdown": "...", "categoryId": "work", "revision": 5, "updatedAt": "2026-11-05T20:31:00Z", "deletedAt": null } }

Оставить локальную

Новый UPDATE с baseRevision = 5 и локальным снимком.

Принять серверную

Локальная заметка перезаписывается serverEntity.

Сохранить обе

Локальная версия становится новой заметкой с новым UUID; серверная принимается.

Удаление

При конфликте с tombstone пользователь решает, восстановить ли локальную как новую.

В этом шаге: сервер только обнаруживает конфликт и возвращает снимок. Клиентский UI разрешения — следующий шаг.

Миграция V3

notes

alter table notes add column user_id uuid references users(id); create index notes_user_id_idx on notes(user_id); create index notes_user_updated_idx on notes(user_id, updated_at);

user_id добавляется nullable, чтобы миграция не падала на существующих строках. Все новые заметки создаются с владельцем; операции без владельца не синхронизируются.

change_log

seq bigserial primary key user_id uuid not null references users(id) entity_type text not null entity_id uuid not null operation_id uuid not null unique operation_type text not null revision bigint not null payload jsonb not null device_id uuid not null references devices(id) changed_at timestamptz not null index change_log_user_seq_idx on change_log(user_id, seq)

processed_operations

operation_id uuid primary key user_id uuid not null references users(id) result text not null change_seq bigint processed_at timestamptz not null
Идемпотентность: применяется только APPLIED. Повтор возвращает DUPLICATE. Конфликты и REJECTED не сохраняются как финальный результат и пересчитываются при повторе.

Проверки шага

CREATE

Заметка создаётся с revision 1, changeSeq, владельцем. Повтор operationId → DUPLICATE.

UPDATE

baseRevision совпала → revision +1, pull отдаёт изменение. Несовпадение → CONFLICT.

DELETE

deletedAt, revision +1, tombstone в pull. Повтор со старой версией → CONFLICT.

Ownership

Чужая заметка недоступна: NOT_FOUND/REJECTED, данные не меняются.

Pull

Курсор, limit, hasMore, порядок seq, пустая страница, tombstones.

Batch

Частичный успех: APPLIED + CONFLICT/REJECTED в одном пакете, ошибка одной операции не откатывает другие.

Команды: ./gradlew test, ./gradlew bootJar, локальный curl push/pull с PostgreSQL.
