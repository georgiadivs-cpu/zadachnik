Один путь записи — синхронизация

Клиент всегда пишет в локальную БД и outbox. Сервер принимает только операции синхронизации, проверяет версии и ведёт журнал изменений. Клиенты читают данные из локальной БД и получают изменения через pull.

Идемпотентность

Каждая операция имеет UUID. Повтор не создаёт дубликат и возвращает прежний результат.

Курсор

Монотонный seq. Клиент сохраняет его только после успешного применения страницы.

Tombstone

Удаление — отдельная операция. Курсор не позволяет «воскресить» запись.

Аутентификация устройства

Сервер персональный, поэтому открытая регистрация запрещена. Первый аккаунт создаётся один раз через setup token из окружения сервера. Каждое устройство получает собственную сессию.

Login request

POST /api/v1/auth/login Content-Type: application/json { "email": "owner@example.com", "password": "", "device": { "id": "5d0f...uuid", "name": "MacBook Pro", "platform": "MACOS" } }

Login response

200 OK { "userId": "0b7e...uuid", "accessToken": "", "accessExpiresAt": "2026-11-05T20:45:00Z", "refreshToken": "", "refreshExpiresAt": "2026-12-05T20:30:00Z", "deviceId": "5d0f...uuid" }

Access token

JWT, 15 минут. Содержит userId и deviceId. Не хранится в логах.

Refresh token

Случайный opaque-токен, 30 дней. В БД только SHA-256 хэш. Ротация при refresh.

Повтор refresh

Повторное использование старого токена трактуется как компрометация: сессия устройства отзывается.

Отзыв

Logout или удаление устройства инвалидирует refresh и все access-токены устройства.

Нужно ваше решение: setup token вместо открытой регистрации. Токен задаётся на сервере и используется только при создании первого аккаунта.

Push: пакет операций

Клиент отправляет до 100 операций. Каждая операция обрабатывается отдельно и транзакционно. Частичный успех допустим: клиент сохраняет непринятые операции в outbox.

operation UUIDbaseRevisionдо 100 операций1 MiB

Request

POST /api/v1/sync/push Authorization: Bearer <access> { "operations": [ { "operationId": "a1...uuid", "deviceId": "5d0f...uuid", "entityType": "NOTE", "entityId": "9c...uuid", "operationType": "UPDATE", "baseRevision": 3, "clientTimestamp": "2026-11-05T20:30:00Z", "payload": { "title": "Заметка", "contentMarkdown": "# Текст\n\nОбновлено", "categoryId": "work", "deletedAt": null } } ] }

Response · HTTP 200, даже при конфликте

{ "results": [ { "operationId": "a1...uuid", "status": "APPLIED", "entityId": "9c...uuid", "revision": 4, "changeSeq": 128 }, { "operationId": "b2...uuid", "status": "CONFLICT", "entityId": "7d...uuid", "revision": 9, "serverEntity": { "...": "полный снимок сервера" } }, { "operationId": "c3...uuid", "status": "REJECTED", "code": "VALIDATION_ERROR", "message": "Заголовок обязателен" } ] }

Статусы операции

СтатусЗначениеЧто делает клиент
APPLIEDОперация применена, revision и seq выданыУдаляет операцию из outbox, сохраняет revision
DUPLICATEoperationId уже обрабатывалсяСчитает операцию успешной, удаляет из очереди
CONFLICTbaseRevision не совпалаСохраняет обе версии, показывает разрешение
REJECTEDОшибка валидации или правПомечает операцию, не теряет локальные данные

Правила

Полный снимок

payload содержит полное состояние изменяемых полей. Частичные patch-операции не используются в MVP.

Версия

CREATE — baseRevision = null. UPDATE/DELETE — обязательна. Сервер увеличивает revision на 1.

Повтор

operationId уникален. Повтор с тем же телом — DUPLICATE; с другим телом — REJECTED.

Ошибки

400 — невалидный пакет; 401 — токен; 413 — размер; 429 — лимит. Доменные ошибки — в results.

Pull: изменения после курсора

Сервер отдаёт изменения в порядке возрастания seq. Клиент применяет страницу одной транзакцией и только затем сохраняет новый cursor.

cursor = seqстраница 200максимум 500tombstones включены
GET /api/v1/sync/pull?cursor=127&limit=200 Authorization: Bearer <access> 200 OK { "changes": [ { "seq": 128, "entityType": "NOTE", "entityId": "9c...uuid", "operationId": "a1...uuid", "operationType": "UPDATE", "revision": 4, "originDeviceId": "5d0f...uuid", "changedAt": "2026-11-05T20:30:01Z", "payload": { "...": "полный снимок" } }, { "seq": 129, "entityType": "NOTE", "entityId": "7d...uuid", "operationType": "DELETE", "revision": 3, "payload": { "deletedAt": "2026-11-05T20:31:00Z" } } ], "nextCursor": "129", "hasMore": false }

Порядок применения на клиенте

01Прочитать страницу
→
02Применить в транзакции
→
03Сохранить cursor
→
04Повторить, если hasMore

Локальные pending-операции

Если по сущности есть неподтверждённая операция, входящее изменение не перезаписывает локальную версию молча — создаётся конфликт.

Собственные изменения

Pull возвращает и изменения текущего устройства. Повторное применение снимка идемпотентно.

Пустая страница

nextCursor равен текущему cursor, hasMore=false. Cursor не откатывается.

Сбой

При ошибке применения cursor не двигается; страница будет запрошена снова.

Цикл синхронизации

Рекомендуемый порядок: push → pull → повторять pull при hasMore. Если push вернул конфликт, pull всё равно выполняется: он приносит серверные версии и изменения других устройств.

Конфликты: сохранить обе версии

Автоматический last-write-wins не используется. Конфликт обнаруживается по baseRevision и возвращается клиенту с полным серверным снимком.

Markdown

Обе версии текста сохраняются до решения. Автоматическое слияние не выполняется.

Удаление против правки

Если сервер удалил, а клиент изменил, возвращается tombstone. Пользователь может сохранить локальную как новую заметку.

Задачи

Конфликт по полям задачи. Ручное разрешение, без LWW.

Чек-лист ↔ задача

Один источник истины — задача. Политика одновременного изменения требует отдельного решения.

Нужно ваше решение: для задач и связи чек-лист↔задача предлагается ручное разрешение конфликта; источник истины для состояния — задача. Для Markdown — сохранять обе версии.

Серверная модель для sync

Доменные таблицы хранят текущее состояние и revision. Журнал изменений неизменяем и используется для pull. Обработанные operationId обеспечивают идемпотентность.

users

id, email, password_hash, status, created_at

devices

id, user_id, name, platform, created_at, last_seen_at, revoked_at

refresh_tokens

id, user_id, device_id, token_hash, expires_at, revoked_at, replaced_by

processed_operations

operation_id PK, user_id, result, processed_at

change_log

seq bigserial, user_id, entity_type, entity_id, operation_id, operation_type, revision, payload jsonb, device_id, changed_at

Доменные таблицы

notes, tasks, lanes, categories, links — текущее состояние + revision

Инварианты

seq

Глобально возрастает. Pull фильтрует по user_id и seq > cursor.

revision

Растёт у сущности при каждом изменении. Используется для conflict detection.

transaction

Изменение сущности, запись change_log и processed_operations — в одной транзакции.

tombstone

Удаление — запись с deleted_at и change_log DELETE. Запись не исчезает из журнала.

Вложения

Отложено: метаданные вложений пойдут через sync, но передача файлов требует отдельного решения P-005 и эндпоинтов init/complete. В текущем протоколе только резервируем entityType ATTACHMENT.

Что нужно утвердить

После вашего «ОК» я зафиксирую это в документации. Пункты ниже — не код, а проектные решения.

1. API-стиль: REST + JSON, версия `/api/v1`, единственный путь записи — `sync/push`; CRUD-эндпоинтов для заметок и задач нет.
2. Синхронизация: outbox → push пакетами → server change_log → pull по cursor; operationId, baseRevision, revision, tombstone, идемпотентность.
3. Аутентификация: setup token для первого владельца, затем login устройства; JWT 15 минут + rotate refresh 30 дней; отзыв устройства.
4. Конфликты: без LWW; обе версии сохраняются; ручное разрешение. Для Markdown — обе версии текста.
5. Документы: создать `docs/API_CONTRACTS.md`, `docs/SYNC_PROTOCOL.md`, `packages/contracts/openapi.yaml`; обновить `DECISIONS.md`, `DATA_MODEL.md`, `ARCHITECTURE.md`, `docs/README.md`.
6. Отложено: передача файлов и presigned URL; политика конфликтов задач/чек-листов требует отдельного подтверждения.

Согласованность

Инварианты
