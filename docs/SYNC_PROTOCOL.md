# SYNC_PROTOCOL — протокол синхронизации

**Версия:** 0.1  
**Статус:** accepted (D-021, D-022)  
**Связанные документы:** `docs/API_CONTRACTS.md`, `docs/DATA_MODEL.md`, `docs/ARCHITECTURE.md`

## 1. Цели

- Локальная работа без сервера.
- Отсутствие молчаливой потери данных.
- Идемпотентная повторная отправка.
- Явное обнаружение конфликтов.
- Восстановление после длительного offline.
- Совместимость нескольких устройств одного владельца.

## 2. Термины

| Термин | Значение |
|---|---|
| Operation | Локальная операция создания, изменения или удаления |
| Outbox | Локальная очередь неотправленных операций |
| Revision | Версия сущности на сервере и клиенте |
| Change log | Неизменяемый журнал серверных изменений |
| Seq | Монотонный номер записи change log |
| Cursor | Последний успешно применённый seq |
| Tombstone | Запись удаления, не исчезающая из журнала |
| APPLIED | Операция применена |
| DUPLICATE | Операция уже была обработана |
| CONFLICT | Версия не совпала, нужна ручная развязка |
| REJECTED | Операция отклонена валидацией или правами |

## 3. Сущности и операции

Типы сущностей:

- `NOTE`
- `TASK`
- `LANE`
- `CATEGORY`
- `NOTE_LINK`
- `TASK_NOTE_LINK`
- `ATTACHMENT` (метаданные; файлы отложены)
- `REMINDER`

Текущая реализация синхронизирует `NOTE`, `TASK`, `LANE` и `REMINDER`.
Остальные типы сущностей зарезервированы и возвращают
`UNSUPPORTED_ENTITY`.

Синхронизация задач и дорожек:

- `TASK` содержит полный снимок полей задачи, включая `laneId`,
  `systemState`, категорию, приоритет и плановые/фактические даты;
- `LANE` содержит название и порядок; удаление непустой дорожки
  отклоняется;
- дорожки по умолчанию имеют стабильные UUID и создаются на сервере
  при setup, а на клиенте — при инициализации локальной БД;
- история перемещений задачи хранится локально и дедуплицируется
  по `operationId`; при pull она восстанавливается из изменений
  `laneId`;
- связи задач с заметками и чек-листами пока не синхронизируются;
- `REMINDER` содержит `taskId` и `remindAt` в UTC, одно активное
  напоминание на задачу; системные уведомления планируются локально
  на каждом устройстве и пересобираются после sync.

Типы операций:

- `CREATE` — новая сущность, `baseRevision = null`;
- `UPDATE` — полный снимок изменяемых полей, `baseRevision` обязательна;
- `DELETE` — удаление, `baseRevision` обязательна.

Восстановление после удаления в MVP выполняется как `UPDATE` с
`deletedAt = null`, если это разрешено доменными правилами сущности.

## 4. Локальная операция

```json
{
  "operationId": "uuid",
  "deviceId": "uuid",
  "entityType": "NOTE",
  "entityId": "uuid",
  "operationType": "UPDATE",
  "baseRevision": 3,
  "clientTimestamp": "2026-11-05T20:30:00Z",
  "payload": {
    "title": "Заметка",
    "contentMarkdown": "# Текст",
    "categoryId": "work",
    "deletedAt": null
  }
}
```

Правила:

- `operationId` генерируется клиентом и не меняется при повторе.
- `deviceId` постоянен для устройства.
- `entityId` — UUID сущности.
- `payload` — полный снимок изменяемых полей, а не частичный patch.
- `clientTimestamp` не используется для определения порядка.
- Секреты и лишние персональные данные в payload не попадают.

## 5. Локальная фиксация

1. Пользователь изменяет сущность.
2. В одной локальной транзакции:
   - обновляется сущность и её локальная revision;
   - создаётся операция в `sync_outbox`.
3. UI сразу видит локальное изменение.
4. Сетевой вызов не является условием сохранения.

Если приложение закрылось до отправки, операция остаётся в outbox.

## 6. Push

1. Клиент выбирает pending-операции в порядке создания.
2. Отправляет пакет до 100 операций.
3. Сервер проверяет токен, устройство, структуру, права и версию.
4. Каждая операция обрабатывается в отдельной транзакции:
   - проверка `operationId`;
   - проверка `baseRevision`;
   - применение к доменной таблице;
   - увеличение `revision`;
   - запись в `change_log`;
   - запись в `processed_operations`.
5. Сервер возвращает результат по каждой операции.

Пакет не является all-or-nothing. Клиент обязан обработать каждый результат.

### 6.1. APPLIED

- Операция удаляется из outbox.
- Локальная revision обновляется серверной.
- `changeSeq` сохраняется для диагностики.

### 6.2. DUPLICATE

- Операция считается успешной и удаляется из outbox.
- Повтор с тем же `operationId` и другим телом — `REJECTED`.

### 6.3. CONFLICT

- Операция не применяется.
- Сервер возвращает полный `serverEntity` и его revision.
- Клиент сохраняет обе версии до решения пользователя.
- Локальные данные не перезаписываются молча.

### 6.4. REJECTED

- Операция не применяется.
- Клиент помечает её и показывает понятную ошибку.
- Локальные данные сохраняются.
- Автоматический бесконечный повтор запрещён.

## 7. Pull

1. Клиент читает cursor из локального хранилища.
2. Запрашивает страницу изменений после cursor.
3. Применяет страницу в одной транзакции.
4. Сохраняет `nextCursor` только после успешного применения.
5. Повторяет запрос при `hasMore = true`.

Правила:

- изменения возвращаются по возрастанию `seq`;
- tombstones включаются;
- собственные изменения устройства также возвращаются;
- повторное применение снимка идемпотентно;
- при ошибке cursor не сдвигается;
- страница не должна частично применяться.

## 8. Порядок синхронизации

Рекомендуемый цикл:

```text
push → pull → repeat pull while hasMore
```

Если push вернул конфликт, pull всё равно выполняется: он приносит
серверные версии и изменения других устройств.

## 9. Конфликты

Универсальный last-write-wins запрещён.

### 9.1. Изменение против изменения

- `baseRevision` не совпала → `CONFLICT`.
- Сохраняются обе версии.
- Пользователь выбирает:
  - оставить локальную;
  - принять серверную;
  - сохранить обе.

### 9.2. Удаление против изменения

- Если сервер удалил сущность, возвращается tombstone.
- Пользователь может сохранить локальную версию как новую сущность.
- Молчаливое воскрешение удалённой сущности запрещено.

### 9.3. Markdown

- Обе версии текста сохраняются до решения.
- Автоматическое слияние не выполняется.

### 9.4. Задачи и чек-листы

- Конфликт задачи разрешается вручную.
- Для связанного пункта чек-листа и задачи источник истины состояния —
  задача; обновление проходит через один application-сценарий.
- Точная политика одновременного изменения пункта и задачи остаётся
  открытым вопросом до отдельного решения.

## 10. Идемпотентность

- `operationId` уникален.
- Повторная доставка не создаёт вторую сущность и второе изменение.
- Сервер хранит результат обработанной операции.
- Клиент может безопасно повторять push после сетевого сбоя.
- `DUPLICATE` не считается ошибкой.

## 11. Ошибки и повтор

| Ситуация | Действие |
|---|---|
| Нет сети | Оставить операции в outbox |
| `429` / `5xx` | Повторить с экспоненциальной задержкой |
| `401` | Обновить access token и повторить один раз |
| `400` / `413` | Не повторять, показать ошибку |
| `CONFLICT` | Сохранить конфликт, запросить решение |
| `REJECTED` | Пометить операцию, не терять локальные данные |

Backoff ограничивается максимальной задержкой; бесконечный цикл
без паузы запрещён.

## 12. Tombstones

- Удаление не удаляет строку change log.
- Клиент получает tombstone через pull.
- Tombstone содержит `deletedAt` и revision.
- Повторное удаление с актуальной revision идемпотентно.
- Восстановление выполняется отдельной операцией по доменным правилам.

## 13. Вложения

- Метаданные вложения могут передаваться как `ATTACHMENT`.
- Файл не передаётся через sync push.
- Недогруженный файл не считается доступным.
- Передача файлов, checksum и presigned URL требуют отдельного решения
  (P-005) и отдельного контракта.

## 14. Безопасность

- TLS обязателен.
- Каждая операция проверяет владельца.
- `deviceId` привязан к активной сессии.
- Отозванное устройство не может push/pull.
- Размер пакета ограничен.
- Содержимое заметок не логируется.
- Секреты не попадают в outbox, change log и тестовые данные.

## 15. Обязательные тесты

- offline → online;
- повторная отправка той же операции;
- повтор с тем же operationId и другим телом;
- разрыв соединения в середине пакета;
- две операции с одинаковым operationId;
- параллельное изменение на двух устройствах;
- удаление против редактирования;
- длительное отсутствие устройства;
- восстановление после переустановки клиента;
- сервер недоступен при запуске;
- cursor не двигается при ошибке применения;
- повторный pull не создаёт дубликаты.
