# Architecture — архитектура приложения

Статус: целевая архитектурная схема.
Конкретный технологический стек не утверждён.

## 1. Архитектурные цели

- Четыре платформы: Android, iOS, macOS, Windows.
- Offline-first.
- Безопасная синхронизация между устройствами.
- Сохранность данных при сбоях сети и сервера.
- Независимость продуктовой логики от UI и инфраструктуры.
- Контролируемые операции AI.
- Возможность развивать систему без переписывания доменной логики.

## 2. Логическая архитектура

### Клиент

- Presentation/UI.
- Application/use-case layer.
- Domain layer.
- Local persistence.
- Sync engine.
- Platform adapters: файлы, уведомления, фоновые задачи,
  безопасное хранилище.

### Сервер

- API.
- Authentication and authorization.
- Domain/application services.
- Central database.
- Change log/sync service.
- Attachment service.
- Backup/restore jobs.
- Audit logging.

### Взаимодействие

Клиент обращается к локальному хранилищу для пользовательских операций.

Синхронизация передаёт изменения серверу через API.

Сервер не должен требовать постоянного соединения клиента
для сохранения локальной работы.

## 3. Утверждённая инфраструктура

Пользователь утвердил:

- размещение сервера на собственном постоянно доступном компьютере;
- отдельное собственное резервное хранилище;
- Flutter + Dart на клиентах (D-015);
- SQLite + Drift на каждом клиенте (D-016);
- Kotlin + Spring Boot и PostgreSQL + Flyway на сервере (D-017);
- монорепозиторий `apps/client`, `services/api`, `packages/contracts`,
  `infrastructure`, `tests` (D-018).

Утверждены:

- API и синхронизация (D-019, D-021) — см. `docs/API_CONTRACTS.md`
  и `docs/SYNC_PROTOCOL.md`.

Открыты и требуют отдельного решения:

- VPN для удалённого доступа (P-004).

Не считать открытые пункты утверждёнными до записи решения
в `DECISIONS.md`.

## 4. Принципы клиента

- UI не обращается к БД напрямую.
- Бизнес-правила находятся в domain/application слоях.
- Локальная операция сначала фиксируется локально,
  затем попадает в outbox.
- Ошибка синхронизации не должна откатывать локальную операцию.
- Сетевые запросы должны иметь тайм-ауты и повторные попытки.
- Повторные запросы должны быть идемпотентными.
- Фоновые возможности платформ не должны быть условием
  корректности данных.

## 5. Протокол синхронизации

Утверждённый поток (D-019, D-021). Детали — в `docs/SYNC_PROTOCOL.md`.

1. Клиент формирует локальную операцию с UUID операции
   и UUID устройства.
2. Операция сохраняется в локальном outbox в одной транзакции
   с изменением локальной сущности.
3. Клиент отправляет пакет операций.
4. Сервер проверяет авторизацию, версию, структуру и допустимость.
5. Сервер применяет операцию транзакционно и записывает
   серверный change sequence.
6. Клиент получает подтверждение принятых операций.
7. Клиент запрашивает изменения после последнего sync cursor.
8. Клиент применяет изменения локально транзакционно
   и обновляет cursor.

Требования:

- повтор операции не создаёт дубликат;
- подтверждение сервера идентифицирует принятые операции;
- курсор продвигается только после успешного применения пакета;
- частичная ошибка не приводит к потере неприменённых изменений;
- удаление передаётся как tombstone;
- конфликт фиксируется явно.

## 6. Конфликты

Утверждённая базовая политика (D-022):

- last-write-wins не используется;
- при несовпадении baseRevision сервер возвращает конфликт
  и полный снимок;
- обе версии сохраняются до решения пользователя;
- для Markdown сохраняются обе версии текста;
- удаление против редактирования возвращает tombstone.

Открыто: точная политика одновременного изменения задачи и связанного
пункта чек-листа. Источник истины состояния — задача, но правила
разрешения конфликта требуют отдельного решения.

## 7. Вложения

Передача вложений отделена от синхронизации метаданных (D-031).

- метаданные и attachment ID фиксируются в PostgreSQL;
- файл хранится на собственном сервере в `ATTACHMENTS_DIR`;
- контролируются размер, MIME type, сигнатура, SHA-256 и завершённость загрузки;
- недогруженные файлы не отображаются как доступные;
- повторная загрузка идемпотентна;
- metadata идёт через attachment API и change log, файл — отдельно;
- `ATTACHMENTS_DIR` входит в резервные копии.

## 7.1. Резервное копирование

Копии создаются вручную из приложения или CLI (D-033).

- `BACKUP_DIR` находится на отдельном диске, вне `ATTACHMENTS_DIR`;
- архив содержит дамп PostgreSQL, вложения, manifest и последние
  снимки устройств;
- архив шифруется `age` ключевым файлом; ключ хранится с правами
  `0600`, офлайн-копия — отдельно;
- снимки локальных SQLite и журнала AI загружаются на сервер и
  шифруются при приёме; хранятся последние 3 на устройство;
- политика хранения: 7 последних + 4 недельных + 6 месячных;
- состояние и история хранятся в JSON рядом с архивами, чтобы статус
  был доступен при недоступной БД;
- проверка: SHA-256, manifest, `pg_restore --list`;
- восстановление из приложения не перезаписывает рабочую БД;
  CLI восстанавливает только в новую БД и папку.

## 8. Доступ и сеть

Рекомендуется частная VPN-сеть для устройств.

Не выставлять БД напрямую в интернет.

Внешний доступ проходит через API с аутентификацией и TLS.

Сервер должен:

- запускаться после перезагрузки;
- иметь контролируемые обновления;
- иметь мониторинг доступности и места на диске;
- не засыпать;
- иметь резервное питание по возможности.

Постоянная доступность зависит от питания, сети, ОС
и домашнего интернет-канала.

## 9. Миграции и версии

- Версионировать схему локальной и центральной БД.
- Миграции должны быть контролируемыми.
- Перед миграцией серверных данных — резервная копия.
- Проверять совместимость клиента и сервера по версиям протокола.
- Старый клиент не должен молча разрушать данные,
  созданные новой версией.

## 10. Архитектурные запреты

- Не синхронизировать один SQLite-файл через файловое облако.
- Не выполнять SQL из UI-компонентов.
- Не позволять AI произвольный SQL или файловый доступ.
- Не хранить секреты в репозитории.
- Не отправлять содержимое заметок в сторонние сервисы без согласия.
- Не использовать сетевую доступность как условие локального сохранения.
