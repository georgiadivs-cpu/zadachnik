# Decision Log — журнал решений

Этот файл разделяет решения пользователя, технические рекомендации
и открытые вопросы.

Агент не должен повышать статус Proposed до Accepted самостоятельно.

## Статусы

- accepted — решение явно принято пользователем;
- proposed — рекомендация ожидает согласования;
- open — решения нет;
- deferred — отложено;
- rejected — отклонено;
- superseded — заменено более новым решением.

## Принятые инфраструктурные решения

### D-012 — Сервер
- Статус: accepted
- Решение: сервер синхронизации размещается на собственном компьютере.

### D-013 — Доступность сервера
- Статус: accepted
- Решение: сервер должен быть постоянно доступен.
- Примечание: фактическая доступность зависит от питания,
  сети, ОС и оборудования.

### D-014 — Резервное хранилище
- Статус: accepted
- Решение: собственное/отдельное резервное хранилище.
- Открыто: NAS, внешний диск или отдельный компьютер;
  точная схема не выбрана.

### D-015 — Клиентский стек
- Статус: accepted
- Дата: 2026-11-05
- Контекст: первая версия должна работать на Android, iOS, macOS и Windows.
- Решение: Flutter + Dart; управление состоянием — Riverpod.
- Кто утвердил: пользователь.
- Последствия: один клиентский код на четыре платформы; сборка Windows
  проверяется на Windows-машине или в CI с Windows.

### D-016 — Локальное хранилище
- Статус: accepted
- Дата: 2026-11-05
- Контекст: offline-first и независимость локальной работы от сервера.
- Решение: SQLite на каждом устройстве, доступ через Drift.
- Кто утвердил: пользователь.
- Последствия: локальная схема версионируется и мигрирует без потери outbox.

### D-017 — Серверный стек
- Статус: accepted
- Дата: 2026-11-05
- Контекст: сервер синхронизации размещается на собственном компьютере.
- Решение: Kotlin + Spring Boot; PostgreSQL; миграции через Flyway.
- Кто утвердил: пользователь.
- Последствия: серверные модули и API развиваются отдельно от клиента;
  версии протокола синхронизации должны быть совместимы.

### D-018 — Структура репозитория
- Статус: accepted
- Дата: 2026-11-05
- Решение: монорепозиторий с каталогами `apps/client`, `services/api`,
  `packages/contracts`, `infrastructure`, `tests`, `docs`, `ai`.
- Кто утвердил: пользователь.
- Последствия: клиент, сервер и контракты версионируются вместе.

### D-019 — API и способ записи
- Статус: accepted
- Дата: 2026-11-05
- Решение: REST API с префиксом `/api/v1`; единственный путь записи
  пользовательских данных — `POST /sync/push`; CRUD-эндпоинтов для
  заметок и задач нет.
- Кто утвердил: пользователь.
- Последствия: клиент и сервер используют один контракт синхронизации;
  см. `docs/API_CONTRACTS.md`.
- Заменяет: P-003 в части API и записи.

### D-020 — Аутентификация устройств
- Статус: accepted
- Дата: 2026-11-05
- Решение: первый владелец создаётся через setup token; дальнейшая
  регистрация закрыта. Вход привязывает устройство. Access JWT — 15 минут,
  refresh — 30 дней с ротацией и отзывом устройства.
  Пароль — от 12 до 128 символов.
- Кто утвердил: пользователь.
- Последствия: открытая регистрация на сервере запрещена; refresh-токен
  хранится только как хэш.

### D-021 — Протокол синхронизации
- Статус: accepted
- Дата: 2026-11-05
- Решение: локальный outbox → push пакетами → серверный change log →
  pull по cursor. Используются operationId, baseRevision, revision,
  монотонный seq, tombstone и идемпотентная обработка. Push возвращает
  результат по каждой операции; частичный успех допустим.
- Кто утвердил: пользователь.
- Последствия: cursor сдвигается только после успешного применения;
  см. `docs/SYNC_PROTOCOL.md`.
- Заменяет: P-003 в части синхронизации.

### D-022 — Политика конфликтов
- Статус: accepted
- Дата: 2026-11-05
- Решение: last-write-wins не используется. При несовпадении baseRevision
  сервер возвращает конфликт и полный снимок; обе версии сохраняются до
  решения пользователя. Для Markdown сохраняются обе версии текста.
- Кто утвердил: пользователь.
- Открыто: точная политика одновременного изменения задачи и связанного
  пункта чек-листа.

### D-023 — Клиентская сессия
- Статус: accepted
- Дата: 2026-11-05
- Решение: access/refresh/userId/deviceId/email хранятся в secure storage
  платформы. Logout очищает токены, но не локальную БД и outbox.
- Кто утвердил: пользователь.
- Последствия: при наличии сохранённой сессии приложение открывается
  без повторного входа; сетевые ошибки не разлогинивают пользователя.

### D-024 — Secure storage на macOS
- Статус: open
- Дата: 2026-11-05
- Контекст: macOS Keychain требует entitlement и подписи.
- Текущее состояние: локальная debug-сборка использует legacy Keychain
  без app sandbox; интеграционный тест secure storage проходит.
- Требуется решение: настроить development signing, Keychain entitlement
  и sandbox для Mac App Store или выбрать другой способ распространения.

### D-025 — Первичная настройка владельца
- Статус: accepted
- Дата: 2026-11-05
- Решение: setup token вводится вручную только на экране первичной
  настройки. После создания владельца регистрация в клиенте недоступна.
- Кто утвердил: пользователь.

### D-026 — Markdown-рендерер и режим предпросмотра
- Статус: accepted
- Дата: 2026-11-06
- Контекст: нужен предпросмотр Markdown на четырёх платформах без
  собственного парсера и без сетевых вызовов.
- Рассмотренные варианты: `flutter_markdown` (прекращён),
  `markdown_widget` (MIT, больше зависимостей), собственный рендерер.
- Решение: `flutter_markdown_plus 1.0.12` (BSD-3), режим переключения
  «Редактор / Предпросмотр»; внешние изображения не загружаются,
  ссылки не открываются автоматически.
- Кто утвердил: пользователь.
- Последствия: Markdown рендерится в GFM-совместимом виде; сетевая
  приватность заметки не зависит от содержимого Markdown.

### D-027 — Синхронизация TODO-доски
- Статус: accepted
- Дата: 2026-11-06
- Контекст: этап 7 добавляет одну доску, задачи, дорожки и историю
  перемещений; данные должны работать на всех устройствах.
- Решение: в MVP используется одна неявная доска; дорожки принадлежат
  пользователю. Дорожки по умолчанию имеют стабильные UUID, одинаковые
  на клиенте и сервере. Синхронизируются `LANE` и `TASK`.
  История перемещений хранится локально, дедуплицируется по
  `operationId` и восстанавливается из change log при pull.
- Кто утвердил: пользователь (объём этапа 7).
- Последствия: отдельная сущность `BOARD` пока не синхронизируется;
  добавление нескольких досок потребует миграции. Связи задач
  с заметками и чек-листами отложены до отдельного решения.

### D-028 — Напоминания и локальные уведомления
- Статус: accepted
- Дата: 2026-11-06
- Контекст: календарь должен показывать задачи и напоминания,
  а уведомления должны работать на четырёх платформах.
- Решение: одно активное напоминание на задачу; время хранится в UTC
  и отображается в локальной IANA-зоне; `REMINDER` синхронизируется.
  Уведомления планируются локально на каждом устройстве через
  `flutter_local_notifications`, `timezone` и `flutter_timezone`.
  При старте и после sync выполняется reconcile; отмена задачи
  удаляет напоминание. Планируется не более 64 ближайших уведомлений.
- Кто утвердил: пользователь.
- Последствия: несколько устройств могут показать одно и то же
  уведомление; внешние календари и повторяющиеся события не входят.
  На Windows отмена уведомлений без MSIX ограничена.
