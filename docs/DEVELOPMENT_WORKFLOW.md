# Development Workflow — процесс разработки

## 1. Общий цикл

1. Получить задачу от пользователя.
2. Прочитать релевантные требования и skills.
3. Проверить, достаточно ли требований для реализации.
4. Выделить допущения и открытые вопросы.
5. Подготовить план и список файлов.
6. Получить подтверждение для значимых решений и рисков.
7. Реализовать минимальный согласованный объём.
8. Запустить тесты, анализаторы и сборки.
9. Обновить документацию.
10. Представить отчёт и указать непроверенное.

## 2. Уточнение задачи

Перед началом реализации определить:

- какую пользовательскую проблему решаем;
- какое поведение ожидается;
- какие платформы затронуты;
- есть ли влияние на локальную БД, синхронизацию,
  безопасность или данные;
- какие критерии приёмки применимы.

Если ответ требует продуктового решения, не угадывать.

## 3. Планирование

План должен включать:

- этапы;
- затрагиваемые модули;
- изменения данных и API;
- риски;
- тесты;
- необходимость миграции;
- необходимость подтверждения.

## 4. Реализация

- Делать небольшие изменения.
- Не смешивать рефакторинг и функциональность без необходимости.
- Сначала тестировать доменную логику.
- Использовать транзакции для согласованных изменений.
- Учитывать offline и повторную синхронизацию.
- Не выполнять сетевые операции в UI-потоке.
- Не блокировать локальное сохранение из-за сервера.

## 5. Проверки

В зависимости от изменения:

- форматирование;
- lint/static analysis;
- unit tests;
- integration tests;
- migration tests;
- sync tests;
- security tests;
- сборки всех целевых платформ;
- ручные сценарии.

Если среда не позволяет выполнить проверку на конкретной
платформе, явно указать это.

## 6. Миграции

До миграции:

- описать изменение схемы;
- определить совместимость старых клиентов;
- создать резервную копию;
- проверить на копии данных;
- определить откат или восстановление;
- запросить согласование, если есть риск потери данных.

## 7. Изменение документации

Изменение продуктового поведения → PRODUCT_SPEC.md.

Изменение компонентов/границ → ARCHITECTURE.md.

Изменение сущностей/связей → DATA_MODEL.md.

Изменение угроз/защит → SECURITY.md.

Изменение интерфейса → UI_UX.md.

Изменение критериев → ACCEPTANCE_CRITERIA.md.

Новое решение → DECISIONS.md.

## 8. Отчёт

Отчёт содержит:

- краткий результат;
- перечень изменённых файлов;
- тесты с фактическими результатами;
- сборки и платформы;
- известные ограничения;
- риски;
- вопросы и следующий шаг.

Не скрывать проваленные тесты.
