# CODING_STANDARDS.md

# Ежедневник — стандарты написания кода

**Версия:** 2.0  
**Статус:** обязательно к исполнению после выбора стека  
**Связанные документы:** `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/DATA_MODEL.md`, `ai/AI_RULES.md`

---

## 1. Общие принципы

- Код читается чаще, чем пишется: ясность важнее краткости.
- Одна функция — одна ответственность.
- Явное лучше неявного.
- Не создавать абстракции без второго реального использования.
- Не дублировать бизнес-правила: правило живёт в одном месте.
- Ошибки обрабатываются, а не подавляются.
- Имена отражают предметную область, а не тип данных.
- Любая оптимизация начинается с измерения.

---

## 2. Технологический стек

Стек утверждён в `docs/DECISIONS.md`:

- клиент — Flutter + Dart, Riverpod (D-015);
- локальное хранилище — SQLite + Drift (D-016);
- сервер — Kotlin + Spring Boot, PostgreSQL + Flyway (D-017);
- структура — `apps/client`, `services/api`, `packages/contracts`,
  `infrastructure`, `tests` (D-018).

Добавление новой зависимости требует обоснования: назначение, лицензия,
поддержка, размер, совместимость с Android, iOS, macOS и Windows.

Специфические правила стека — в §13. Общие правила ниже действуют
независимо от платформы.

## 3. Структура и слои

| Слой | Содержит | Не содержит |
|---|---|---|
| Presentation/UI | экраны, состояния, ввод | SQL, правила синхронизации |
| Application | сценарии использования | платформенные вызовы |
| Domain | сущности, правила, интерфейсы | БД, HTTP, UI |
| Data | репозитории, маппинг, API-клиенты | бизнес-правила |
| Platform | адаптеры ОС | доменную логику |

Запрещено:

- UI → репозиторий или БД напрямую;
- доменная сущность → HTTP-клиент или файловая система;
- бизнес-правило в обработчике кнопки;
- дублирование правила на клиенте и сервере без явного источника истины.

---

## 4. Локальные данные и offline-first

- Локальная операция сохраняется до обращения к серверу.
- Изменение сущности и запись в outbox выполняются согласованно.
- Ошибка сети не откатывает локальную операцию.
- Очередь не теряется при перезапуске приложения.
- Повторная отправка идемпотентна.
- Удаление представлено tombstone.
- Курсор синхронизации продвигается только после успешного применения данных.
- Схема локальной БД версионируется; миграции не теряют данные и очередь.
- Рабочий файл SQLite не синхронизируется через Dropbox, iCloud, OneDrive,
  SMB или другую общую папку.

---

## 5. Данные

- Стабильные UUID для сущностей и операций.
- Названия и текст не используются как ключи связей.
- Время хранится однозначно; при необходимости сохраняется временная зона.
- Версии/ревизии используются для обнаружения конфликтов.
- Внешние ключи и ограничения обязательны там, где есть связь.
- Индексы добавляются под конкретный запрос, а не «на всякий случай».
- Большие бинарные файлы не хранятся в основной таблице без обоснования.
- Миграции только вперёд; применённые файлы не редактируются.
- Destructive-изменения выполняются по согласованному плану
  с резервной копией и проверкой восстановления.

---

## 6. Синхронизация и конфликты

- Каждая операция имеет уникальный ID и относится к устройству.
- Сервер проверяет авторизацию, версию и допустимость операции.
- Подтверждение сервера идентифицирует принятые операции.
- Частичная ошибка пакета не теряет неприменённые изменения.
- Конфликт фиксируется явно и не разрешается молча.
- Last-write-wins не используется без утверждённой политики.
- Для текста заметок конфликтующие версии сохраняются до решения пользователя.
- Связанный пункт чек-листа и задача имеют один источник истины;
  обновление проходит через один application-сценарий.

---

## 7. Безопасность

- Секреты только в защищённом хранилище, не в репозитории и не в логах.
- Аутентификация и авторизация проверяются на сервере.
- Входные данные валидируются на клиенте и сервере.
- Файлы проверяются по MIME, сигнатуре, размеру и допустимому типу.
- Пути и архивы обрабатываются безопасно.
- AI не получает произвольный SQL, shell или файловый доступ.
- Внешние сервисы не получают пользовательские данные без согласия.
- Ошибки не раскрывают внутренние детали и секреты.

---

## 8. Ошибки и логи

- Ошибки классифицируются: валидация, доступ, конфликт, хранилище,
  сеть, синхронизация, вложения, AI, неожиданная.
- Пользователю — понятное сообщение; разработчику — код и идентификатор.
- Пустой `catch` запрещён.
- Логи структурированные, с уровнями.
- В логах нет паролей, токенов, ключей, полного текста заметок,
  приватных вложений и иных чувствительных данных.

---

## 9. Тесты

- Название теста описывает ожидаемое поведение.
- Один тест — одна проверяемая мысль.
- Тесты не зависят от порядка выполнения и внешней сети.
- Обязательны негативные и граничные сценарии.
- Тест должен падать при регрессии.
- Моки не заменяют интеграционную проверку критичных сценариев.
- Для исправленного дефекта добавляется regression test, если возможно.
- Результаты тестов и платформа фиксируются в отчёте.

---

## 10. Комментарии и документация

- Комментарий объясняет «почему», а не «что».
- Публичные интерфейсы модулей документируются.
- Не оставлять закомментированный код.
- `TODO` допустим только со ссылкой на задачу и не в завершённой функции.
- Изменение поведения сопровождается обновлением соответствующего документа.

## 11. Именование

| Элемент | Стиль | Пример |
|---|---|---|
| Тип/класс | PascalCase | `NoteEditor` |
| Функция/переменная | camelCase | `createNote` |
| Константа | UPPER_SNAKE_CASE | `MAX_ATTACHMENT_SIZE` |
| Таблица БД | snake_case, множественное | `note_revisions` |
| Поле БД | snake_case | `created_at` |
| JSON-поле | camelCase | `createdAt` |

Стиль конкретного языка уточняется в §13,
но имена должны оставаться предметными.

---

## 12. Коммиты и изменения

- Одно изменение — одна логическая цель.
- Сообщение коммита: что и зачем.
- Не смешивать рефакторинг и функциональность без необходимости.
- Изменение контракта сопровождается обновлением документации.
- Не коммитить секреты, временные файлы и артефакты сборки.

## 13. Правила утверждённого стека

### 13.1. Dart / Flutter

- UI не обращается к Drift напрямую: только через repository/provider.
- Riverpod используется для состояния и зависимостей; бизнес-логика
  находится в application/domain слоях.
- Асинхронные состояния показываются явно: loading, data, error.
- `build()` не содержит бизнес-логики и сетевых вызовов.
- Контроллеры, подписки и ресурсы освобождаются в `dispose`.
- Платформенные вызовы изолируются в адаптерах.
- Локальная операция сохраняется в БД и outbox до сетевого вызова.
- Сборки проверяются для Android, iOS, macOS и Windows; для непроверенной
  платформы это явно указывается в отчёте.

### 13.2. Kotlin / Spring Boot

- Контроллеры тонкие: валидация DTO и вызов application-сервиса.
- Транзакции — на уровне application-сервиса.
- Constructor injection вместо field injection.
- Доменные ошибки преобразуются в HTTP-ответы обработчиком.
- SQL параметризован; конкатенация значений запрещена.
- Публичные API модуля минимальны; детали скрываются.
- Секреты и строки подключения берутся из окружения.
- Интеграционные тесты используют PostgreSQL через Testcontainers.

### 13.3. SQL / PostgreSQL

- UUID для основных сущностей.
- `timestamptz` для времени.
- Внешние ключи и проверки обязательны там, где есть связь.
- Миграции Flyway только вперёд; применённые файлы не редактируются.
- Индексы добавляются под конкретный запрос.
- Удаление пользовательских сущностей — tombstone/soft delete.

### 13.4. Контракты

- API-контракт фиксируется в `packages/contracts` после утверждения протокола.
- Изменение контракта сопровождается обновлением клиента и документации.
- Клиент не считается совместимым, пока контракт не проверен тестом.
